# Test Ideas – Secure Legal Document Upload

Feature: Secure Document Upload\
User Role: Paralegal\
Quality Characteristics: Functionality, Data Integrity, Security

The following test ideas use a risk-based testing approach, focusing on failures that could compromise document confidentiality, corrupt legal evidence, cause incorrect upload behavior, or produce unreliable audit records.

Priority definitions: P0 = Critical, P1 = High, P2 = Medium.

## 1. Functionality

Objective: Verify that supported documents can be uploaded successfully, file size restrictions are enforced, and upload progress is accurately communicated.

| ID  | Test idea                                                                                      | Risk being investigated                                                                        | Priority |
| --- | ---------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- | -------- |
| F01 | Upload valid PDF, DOCX, and TXT documents individually.                                        | Supported file formats may be incorrectly rejected or processed.                               | P1       |
| F02 | Attempt to upload unsupported formats such as EXE, ZIP, JPG, and XLSX.                         | Unsupported documents may be accepted.                                                         | P1       |
| F03 | Upload files of 19.9 MB, exactly 20 MB, and slightly above 20 MB.                              | Incorrect boundary validation may reject valid documents or accept oversized ones.             | P1       |
| F04 | Upload a zero-byte file.                                                                       | Empty or invalid documents may be stored as successful uploads.                                | P2       |
| F05 | Upload documents with special characters, Unicode, Thai characters, and very long filenames.   | Filename handling may cause errors or prevent retrieval.                                       | P2       |
| F06 | Verify progress updates during slow uploads, including 0%, intermediate values, and 100%.      | Progress indicators may freeze, misreport status, or incorrectly imply success.                | P1       |
| F07 | Interrupt the network connection halfway through an upload.                                    | The application may incorrectly report success or fail to handle interruptions.                | P1       |
| F08 | Cancel an upload while it is in progress.                                                      | The system may continue processing a canceled document.                                        | P1       |
| F09 | Upload multiple documents concurrently.                                                        | Concurrent uploads may cause failures, incorrect progress indicators, or mismatched documents. | P1       |
| F10 | Retry an upload after a timeout or server error.                                               | Retries may create duplicate documents or inconsistent results.                                | P1       |
| F11 | Upload documents using different supported browsers.                                           | Browser-specific issues may prevent uploads or affect progress reporting.                      | P2       |
| F12 | Verify that failed uploads display a clear error message and do not display a success message. | Users may believe a legally important document was stored when it was not.                     | P1       |

## 4. Highest-risk end-to-end scenarios

These scenarios combine the acceptance criteria to identify defects that isolated tests might miss.

E2E-01 — Confidentiality after upload

P0

User A uploads a valid PDF successfully. User B attempts access through the application, API, and direct storage URL. Verify that only User A has access and the success event is audited.

E2E-02 — Network failure during upload

P0

Interrupt a DOCX upload at 70%. Verify that the application never reports success, no partial document becomes accessible, and the actual failure outcome is audited.

E2E-03 — File integrity verification

P0

Upload a 20 MB PDF, observe progress, download it, and compare cryptographic hashes. Verify ownership and the corresponding audit record.

E2E-04 — Unauthorized document access

P0

Upload separate documents as two users. Attempt cross-user download, preview, metadata retrieval, and owner-ID manipulation. Verify all unauthorized actions are denied.

E2E-05 — Malicious file bypass

P0

Submit a disallowed file disguised as a PDF directly through the upload API. Verify server-side rejection, safe cleanup, and accurate failure auditing.

## 6. Requirements that need clarification

Several security-sensitive behaviors are not explicitly defined by the acceptance criteria. Clarifying these would make the tests more deterministic.

1. 20 MB definition: Does it mean 20,000,000 bytes or 20 × 1,048,576 bytes? Is the limit per file?
2. Failed upload auditing: Should unsupported file attempts, unauthenticated requests, canceled uploads, and connection failures all generate audit events?
3. Document sharing: The user story mentions sharing, but there are no acceptance criteria for granting, revoking, or limiting access.
4. Progress updates: Must progress be shown as a percentage, or is a status indicator sufficient? Does 100% represent bytes transferred or successful server-side storage?
5. Malware protection: Should suspicious documents be rejected, quarantined, or accepted with warnings?
6. Audit retention: Who can inspect audit entries, how long are they retained, and must they be tamper-evident?

Recommended execution order: Start with P0 security authorization tests, document integrity checks, and audit reliability. Then cover supported formats, boundary values, progress handling, and resilience scenarios. These areas present the greatest risk to confidentiality, evidentiary trustworthiness, and reliable legal workflows.
